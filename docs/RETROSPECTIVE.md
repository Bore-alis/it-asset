# IT 자산 관리 시스템 회고

> 사내 IT 자산 관리 시스템을 만들고 운영하면서 한 설계 판단과 겪은 문제를 정리한 글입니다.
> 회사와 인프라를 특정할 수 있는 정보는 모두 일반화했습니다.

## 1. 왜 만들었나

IT 담당 부서는 장비 지급·회수·교체를 엑셀로 관리하고 있었습니다. 엑셀로는 다음이 어려웠습니다.

- **이력 추적**: 이 노트북을 누가, 언제부터 언제까지 썼는지
- **상태 일관성**: 퇴사자 장비가 회수됐는지, 재고로 돌아왔는지
- **증빙**: 퇴사자 노트북의 데이터를 지웠다는 기록을 일정 기간 보관하는 일
- **안내**: 장비를 지급할 때마다 사용자에게 보내는 안내 메일을 손으로 작성하는 일

그래서 Spring Boot와 Next.js로 웹 시스템을 만들었습니다. 로그인은 사내 Active Directory 계정을 그대로 씁니다.

## 2. 퇴직자 초기화 증적: 3년 보관, 그다음 자동 파기

가장 공을 들인 기능입니다. 요구사항은 이랬습니다.

1. 퇴사 처리를 하면 그 사람이 쓰던 **노트북·PC**를 초기화 대상으로 올린다.
2. 담당자가 초기화한 뒤 방식, 일시, 스크린샷을 증적으로 남긴다.
3. 증적은 **3년 보관**하고, 기한이 지나면 **파일까지 지운다**.

### 원본 데이터와 수명이 다르다

처음에는 증적 테이블이 `employees`와 `assets`를 외래키로 참조하게 하려 했습니다. 그런데 사원 정보는 퇴사 후 삭제될 수 있고, 자산도 폐기되면 지워집니다. 그러면 3년 보관해야 할 증적이 참조 무결성 때문에 같이 지워지거나, 원본 삭제가 막힙니다.

그래서 **외래키를 일부러 걸지 않고**, 사원명·소속·모델명·S/N을 증적을 만드는 시점의 **스냅샷**으로 복사해 두었습니다. 증적은 "그때 그 장비를 그 사람이 썼다"는 기록이라 스냅샷이 맞는 모델이었습니다.

```sql
-- 주의: employees / assets 로의 FK를 일부러 걸지 않는다.
--       사원 정보나 자산이 삭제되어도 3년 보관 의무가 있는 증적은 독립적으로 남아야 하므로,
--       사원명 · 소속 · 모델명 · S/N 은 참조가 아니라 생성 시점의 스냅샷 값으로 보관한다.
```

반대로 첨부파일 메타데이터(`asset_wipe_files`)는 증적 없이는 의미가 없으므로 `ON DELETE CASCADE`로 묶었습니다.

### 퇴사 시점에 스냅샷을 먼저 뜬다

퇴사 처리는 자산을 회수하면서 `assets.current_user_id`를 비웁니다. 회수한 뒤에는 "누가 쓰던 장비인지"를 알 수 없으므로, **회수하기 전에** 사원 정보와 보유 자산을 먼저 조회해 두고 같은 트랜잭션 안에서 증적을 만듭니다. 모니터처럼 저장장치가 없는 장비는 대상에서 뺐습니다.

### 자동 파기는 되돌릴 수 없다

매일 새벽 3시에 스케줄러가 기한이 지난 증적을 지웁니다. 되돌릴 수 없는 작업이라 다음을 지켰습니다.

- DB 행을 먼저 지우고, 디스크의 파일과 폴더를 정리합니다.
- 무엇을 지웠는지 **건별로 로그**를 남깁니다. (증적 번호, 자산, 퇴직자, 초기화일, 만료일, 첨부 수)
- 아직 초기화하지 않은 '대기' 건은 만료일이 없어서 **파기되지 않습니다**.
- 보관 연수와 실행 주기는 환경변수로 바꿀 수 있습니다.

검증은 운영 DB를 건드리지 않고, **별도 DB에 20초 주기 cron**으로 백엔드만 따로 띄워서 했습니다. 만료 건은 사라지고, 미만료 건과 '대기' 건은 남고, 로그가 찍히는지 확인했습니다.

### 파일 저장

- 저장 파일명은 서버가 UUID로 새로 만듭니다. 원본 파일명을 경로에 쓰면 경로 조작 위험이 있기 때문입니다. 원본 이름은 화면 표시용으로만 DB에 둡니다.
- 이미지와 PDF만 받습니다.
- 첨부 폴더는 **도커 볼륨으로 마운트**해야 합니다. 마운트가 없으면 재배포할 때마다 3년 보관해야 할 파일이 사라집니다. 그래서 이 조건을 자동으로 확인하는 점검 스크립트를 만들었습니다.

## 3. 트러블슈팅: 스크린샷 첨부가 "용량 초과"로 실패

### 증상

운영 이관 후 증적 첨부가 "파일 용량(1건당 20MB)을 확인해주세요"라는 알림과 함께 실패했습니다. 올린 파일은 몇 MB짜리 스크린샷이었습니다.

### 헷갈렸던 이유

1. nginx 설정 파일에는 `client_max_body_size 60m;`가 **들어 있었습니다.** 컨테이너 안에서 `cat`으로 봐도 있었습니다.
2. 프론트엔드가 응답 body를 버리고 `response.ok`만 보고 있어서, **413이든 400이든 500이든 같은 문구**가 떴습니다.

### 원인 좁히기

같은 파일을 두 경로로 보내 봤습니다.

| 경로 | 결과 |
|---|---|
| nginx 경유 | **413** |
| 백엔드 직접 | 정상 도달 |

`localhost`로 보냈으니 로드밸런서는 경로에 없습니다. nginx에서 막힌 게 확정됐습니다.

### 원인

nginx 설정 파일은 **바인드 마운트**였습니다. 파일을 고치면 컨테이너 안에서도 새 내용이 바로 보이지만, **nginx는 기동할 때만 설정을 읽습니다.** 이관 과정에서 설정만 고치고 컨테이너를 다시 띄우는 단계가 빠져서, nginx는 기본값 1MB로 돌고 있었습니다.

```bash
docker exec <nginx 컨테이너> nginx -s reload   # 무중단으로 해결
```

### 배운 것

- **설정 파일에 값이 있다고 프로세스가 그 값으로 도는 것은 아니다.** 설정을 확인할 때는 파일이 아니라 동작을 봐야 합니다.
- **경로를 나눠서 보내면 원인을 빨리 좁힐 수 있다.** 프록시가 여러 겹이면 한 겹씩 빼고 같은 요청을 보내 봅니다.
- **에러 응답 body를 버리면 안 된다.** 백엔드는 실패 사유를 한국어로 body에 담아 보내고 있었는데, 화면이 그걸 버려서 진단이 늦어졌습니다. 개발자 도구 Network 탭의 Response에서는 바로 보였습니다.

## 4. 트러블슈팅: 배포했는데 백엔드가 그대로

기존 배포 스크립트로 올렸는데 백엔드 변경이 반영되지 않았습니다.

Dockerfile은 `COPY build/libs/*SNAPSHOT.jar app.jar`로 **`build/libs/`에서** jar를 가져오는데, 스크립트는 새 jar를 `backend/` 바로 아래에만 복사하고 있었습니다. `build/libs/`에 남아 있던 **옛 jar로 이미지가 계속 만들어지고** 있었던 겁니다.

새 배포 스크립트는 jar를 두 경로 모두에 두고, 배포 전후로 **컨테이너 안에서 실행 중인 jar의 크기를 비교**해서 반영 여부를 출력합니다. "배포 성공"이라는 메시지 대신 실제로 바뀌었는지를 보여주도록 한 것입니다.

## 5. SSH 없는 운영서버에 배포하기

운영서버에는 SSH가 없고 **FileZilla로 파일 전송만** 됐습니다. 원격으로 명령을 여러 번 칠 수 없으니, "파일 하나 올리고 스크립트 하나 실행"으로 끝나야 했습니다.

```
[개발서버] make-prod-bundle.sh
    빌드 → 필요한 파일만 수집 → prod-bundle_<시각>.tar.gz
        │  FileZilla 업로드
[운영서버] deploy-all.sh
    0) 실행 중인 jar 백업 (롤백 지점)
    1) 번들 압축 해제
    2) 최초 설정 적용 (이미 적용됐으면 건너뜀)
    3) 스테이징 → 배포 위치 복사 → 컨테이너 재빌드
    4) 검증: jar 반영 여부, 증적 환경 점검, API 응답
```

신경 쓴 점:

- **번들을 작게.** 빌드 캐시와, 운영에 이미 있는 `node_modules`는 뺐습니다. 폴더째 끌어다 놓을 때 생기던 전송 누락도 없어졌습니다.
- **여러 번 실행해도 안전하게.** 최초 설정 스크립트는 `docker-compose.yml`과 nginx 설정을 고치기 전에 타임스탬프 백업을 남기고, 이미 적용된 항목은 건너뜁니다.
- **파일 전송 중 확장자가 바뀌는 경우까지.** `.tar.gz`가 `.tar`로 저장되는 일이 있어서 둘 다 찾고, 폴더 이름은 파일명이 아니라 아카이브 내용에서 읽습니다.
- **첨부파일은 절대 건드리지 않게.** 프론트엔드는 옛 파일이 남지 않도록 비우고 복사하지만, 백엔드 업로드 폴더는 복사 대상에서 뺐습니다.
- **롤백의 한계를 문서로 남겼습니다.** 자동 백업되는 건 백엔드 jar뿐이고, 프론트엔드는 이전 번들을 다시 배포해야 합니다. 그래서 번들을 몇 세대 보관합니다.

## 6. 리팩터링

기능을 붙이기 전에 코드 리뷰를 하고 다음을 정리했습니다.

| 문제 | 조치 |
|---|---|
| 한 컨트롤러가 700줄을 넘고 사원·자산·메일을 다 처리 | 자산 API는 `AssetController`로, 메일 HTML 조립은 `AssetHistoryMailService`로 분리. 기존 URL은 유지 |
| 컨트롤러마다 `try/catch`로 500을 반환해서 `@Transactional` 롤백이 안 일어남 | 예외를 전파시키고 `@RestControllerAdvice`에서 한 번에 처리 |
| NAS 자체 서명 인증서 때문에 **JVM 전역**에서 TLS 검증을 끔 (메일 발송 등 다른 HTTPS까지 영향) | NAS 전용 `RestTemplate`에만 적용 |
| 로그인 아이디가 LDAP 검색 필터에 그대로 들어감 | RFC 4515에 따라 특수문자 이스케이프 |
| 사원명·모델명이 메일 HTML에 그대로 들어감 | HTML 이스케이프 |
| 증적 목록에서 첨부파일을 건별로 조회 (N+1) | `IN` 한 번으로 읽어서 메모리에서 나눠 담음 |
| 필수값 검증이 없음 | `@NotBlank` + `@Valid` |

## 7. 보안 전제

API에 토큰 인증이 없고, CORS를 전체 허용하고, 애플리케이션은 HTTP만 씁니다. 사내망 전용이고, TLS 종료와 출처 제어는 앞단 로드밸런서가 맡고, 로그인은 AD로 한다는 전제에서 고른 구성입니다.

다만 이건 **전제가 깨지면 바로 문제가 되는 선택**이라, 운영 문서에 "외부망 노출을 검토한다면 API 인증, CORS 출처 제한, 첨부파일 접근 제어를 먼저 도입할 것"이라고 조건을 명시해 두었습니다. 취약점을 숨기기보다 **어떤 전제 위에 서 있는지를 기록**하는 쪽을 택했습니다.

## 8. 다음에 한다면

- **API 응답 처리 일원화**: 프론트엔드 공통 fetch 함수가 성공 여부만 돌려주고 실패 사유를 버립니다. 3장의 진단이 늦어진 이유였습니다. 에러 body를 그대로 띄우는 구조로 바꾸고 싶습니다.
- **반복 쿼리 배치화**: 일괄 지급·교체·엑셀 등록은 건마다 쿼리를 날립니다. 지금 데이터 규모에서는 문제가 없지만, MyBatis `foreach` 배치로 바꿀 수 있습니다.
- **테스트**: 파기 스케줄러처럼 되돌릴 수 없는 로직은 수동 검증 대신 통합 테스트로 남겼어야 했습니다.
- **파기 전 알림**: 지금은 기한이 되면 바로 지웁니다. 파기 한 달 전에 담당자에게 알림을 보내면 더 안전합니다.
